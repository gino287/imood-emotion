# GPU 熱啟動：實測結果

> 硬體：RTX 3050 Laptop GPU（4GB），驅動 610.62，最大 SM 2100 MHz
> 環境：Windows 11 → WSL2 → Docker（`imood-emotion` image），torch 2.13.0+cu126
> 模型：`Johnson8187/Chinese-Emotion-Small` @ `2c04ce86`，batch=1，max_length=160
> 資料：`_local/samples.jsonl` 200 句
> 產生：`research/gpu-warmup/experiments/exp1_gap_sweep.py` 等

---

## TL;DR

### 最重要的一件事

> **不用跟降頻對抗。改用 fp16（再加 CUDA Graph）就好。**
>
> | | 現況 | **fp16** | **fp16 + CUDA Graph** |
> |---|---:|---:|---:|
> | 間歇 1.5 秒 p50 | 126.5ms | **61.9ms** | **52.4ms** |
> | 間歇 p95 | 139.1ms | 63.6ms | **53.6ms** |
> | 連續 p50 | 16.0ms | 16.2ms | **4.7ms** |
> | VRAM | 1073 MB | **547 MB** | **539 MB** |
> | 額外功耗 / GPU 佔用 | — | **0** | **0** |
> | 準確率 | 0.85 | **0.85（200 句零差異）** | — |
>
> 心跳（keep-alive）也有效（126.5 → 46.3ms），但要付 **16% 的 GPU 時間 + 5.3W**，
> 而且 p95 比較差（86.7 vs 53.6）。**沒有理由先選心跳。**

### 全部結論

| # | 結論 | 依據 |
|---|---|---|
| 1 | **降頻假設完全成立，而且量到了**：閒置 SM 掉到 210 MHz、連續時 1912 MHz，延遲 139ms vs 17.5ms | exp1 sweep + decay |
| 2 | **沒有「安全的間隔門檻」**——間隔 **50ms** 時延遲就已經翻倍（17.5→33.5ms） | exp1 sweep |
| 3 | **降頻在 0.7 秒內就掉一半**（1927→1170 MHz），5.25 秒觸底 210 MHz | exp1 decay |
| 4 | **回升極快**：閒置 12 秒後，**第 3 句就回到 16ms**。懲罰只落在前 1~2 句 | exp1 decay |
| 5 | **WSL2 容器內鎖不了時脈**（`-lgc` 回 Unknown Error），persistence mode 對此無效 | 直接實測 |
| 6 | **便宜的心跳（小 matmul）完全無效**；真正的變數是「GPU 工作佔比」，要 ≥3% 才有感 | exp2 |
| 7 | **fp16 把間歇延遲砍一半、VRAM 砍一半，準確率零差異** | exp3 + exp4 |
| 8 | **torch.compile / CUDA Graph 只改善連續模式，對間歇模式無效**（推翻我原本的預期） | exp3 |
| 9 | 兩個量測陷阱（見下）——第一版數據被自己的 instrumentation 汙染 | `_nvml_cost.py` |

### 這張表回答了 open_questions 裡的三個問號

**Q1：「降頻是推論出來的，沒有直接量測證實」**
→ ✅ **證實了**。`throttle` 欄位在所有間歇條件下都回報 `GpuIdle`，
   而連續條件是空的。SM 時脈從 1912 掉到 210 MHz，**9.1 倍**；
   延遲從 17.5 漲到 138.8ms，**7.9 倍**。兩個比值對得上，
   確認延遲主要就是時脈造成的，不是別的因素。

**Q2：「降頻的間隔門檻在哪（0.2秒？1秒？）」**
→ ❌ **這個問題的前提是錯的：沒有門檻，是連續劣化。**
   間隔 **50ms** 時延遲就已經是連續模式的 **1.9 倍**，
   100ms 是 3.2 倍，2 秒之後才進入 139ms 的平台。
   **不存在一個「這個間隔以下就安全」的值。**

   > 這對心跳（keep-alive）設計是壞消息：
   > 要維持 17ms，心跳間隔得壓到 **50ms 以下**，
   > 那已經接近「持續佔用 GPU」了，成本不低。

**Q3：「沒測鎖時脈/persistence mode 能不能救」**
→ 見下面「其他手段」一節。**容器內鎖不了。**

### 幾個容易被忽略的欄位

- **stdev**：中段間隔（0.2~1.5s）的標準差高達 23~36ms，
  而兩端（連續、>2s）都在 2~13ms。
  **中間區段不只慢，還特別不穩定** —— governor 在幾檔之間來回，
  同一個間隔下有的句子 60ms 有的 130ms。
  對即時系統來說 **p95 比 p50 重要**，而 p95 從 0.2s 起就已經破 120ms。
- **功耗**：45.6W（連續）vs 12.2W（5 秒間隔）。**差 3.7 倍。**
  這就是「保持熱啟動」要付的電費與熱，不是抽象成本。
- **溫度**：連續模式 81°C。這張筆電卡長時間 80°C 以上會有 thermal 風險，
  心跳方案要考慮這件事。

會完全落在劣化區間——真實對話的句間停頓，剛好就是最糟的那一段。

### 回升（重新開始之後）

| 第幾句 | 延遲 |
|---:|---:|
| 0 | **131.6ms** |
| 1 | **136.1ms** |
| 2 | **16.7ms** ← 已經回來了 |
| 3~17 | 15~17ms |

> **這是整份調查最反直覺、也最有用的一個發現：
> 回升只要 2 句（約 0.27 秒的實際 GPU 工作），不是好幾秒。**

含意：**懲罰是「每次閒置後的前 1~2 句」，不是「整段對話都慢」。**
如果使用者連續講好幾句（句間 < 0.2 秒），只有第一句慢，後面都快。
真正的痛點是「講一句、停三秒、再講一句」這種節奏——每一句都是第一句。

⚠️ 但要注意：這個「2 句就回來」是在 **句間幾乎沒有間隔** 的條件下量的。
從 sweep 表可以看到，如果句間有 1.5 秒，時脈根本升不上去（穩態只有 300 MHz）。
**兩個數字不矛盾：回升需要「連續的工作」，不是「工作過一次」。**

## 其他手段的實測

### `nvidia-smi --lock-gpu-clocks`：容器內失敗，主機端只差一個管理員權限

容器內（WSL2）：

```
$ nvidia-smi -lgc 1000,2100
Unable to set GPU locked clocks "(gpuClockMin 1000, gpuClockMax 2100)"
for GPU 00000000:01:00.0: Unknown Error
Terminating early due to previous errors.
```

（容器內是 root，不是權限問題；是 WSL2 的 NVML shim 沒有實作設定型呼叫。）

**但 Windows 主機端的 `nvidia-smi.exe` 不一樣** —— 2026-08-13 補測：

```
$ /c/Windows/System32/nvidia-smi.exe -lgc 1200,2100
The current user does not have permission to change clocks for GPU 00000000:01:00.0.
```

錯誤訊息從「Unknown Error」變成「**沒有權限**」——
代表主機端的驅動介面**有實作這個功能**，只是需要系統管理員。
這跟 WSL2 shim 的死路是兩回事，**值得用管理員 PowerShell 再試一次**。

主機端 `nvidia-smi` 還能看到容器內看不到的東西：

```
$ nvidia-smi.exe -q -d PERFORMANCE
    Clocks Event Reasons
        Idle                                : Active      ← 降頻原因，驅動自己承認
        SW Power Cap                        : Not Active
        HW Slowdown                         : Not Active
```

**降頻假設的最直接證據**：不是溫度、不是功耗上限，就是「閒置」。
（也順帶說明為什麼所有散熱/限電方向的調整都不會有用。）

支援的時脈檔位也查得到（2100 / 2092 / 2085 / … MHz），
代表 `-lgc` 的參數空間是開放的。

### Persistence mode：⚠️ 回報成功但無效

```
$ nvidia-smi -pm 1
Persistence mode is already Enabled for GPU 00000000:01:00.0.
```

**已經是開的，時脈照樣掉到 210 MHz。**
證明 persistence mode 解的是「驅動載入」（L1/L3），不是降頻（L4）。
網路上很多文章把兩者混為一談。

### 其他 NVML 限制

| 查詢 | WSL2 結果 |
|---|---|
| `nvmlDeviceGetPowerManagementLimit` | `NotSupported` |
| `nvidia-smi -q -d POWER` 的 power limit | 60W（從 nvidia-smi 讀得到，NVML API 讀不到）|
| supported clocks 清單 | ✅ 讀得到（2100 / 2092 / 2085 / 2077 …）|

### ⏳ 尚未測試：NVIDIA 控制面板「偏好最大效能」

**這是最有希望的一招，但需要在 Windows 主機端手動設定，我沒有代為更動系統設定。**

```
NVIDIA 控制面板 → 管理 3D 設定 → 全域設定 → 電源管理模式
  → 改成「偏好最大效能」
```

改完之後重跑：

```bash
docker compose -f docker/docker-compose.yml run --rm app \
    python research/gpu-warmup/experiments/exp1_gap_sweep.py --mode sweep
```

**比較 `gap=1.5s` 那一列的 p50 有沒有從 125ms 掉下來。**
如果有效，這就是最乾淨的解——不用寫任何程式、不用心跳、不搶資源。

⚠️ 但預期會有代價：閒置功耗上升 10~30W（社群數據），
筆電電池與散熱都會受影響。而且它是 **全域設定**，
會影響機器上所有 GPU 程式。

⚠️ 還有一個限制：這個設定可以「針對單一程式」指定，
但我們的 CUDA 程式跑在 WSL2 容器裡，
**主機看到的執行檔是 WSL 相關的 process，不是我們的 python**，
所以 **只能用全域設定**，沒辦法只針對 BERT 開。

📌 **但先講清楚優先順序**：實驗 3 出來之後，這一招的重要性下降了。
fp16 + CUDA Graph 已經把間歇延遲壓到 52.4ms、而且完全免費。
「偏好最大效能」值得花 5 分鐘試，但 **不是關鍵路徑**，
而且它是環境相關的設定，換到實驗室機/雲端就沒了。

## ⚠️ 兩個量測陷阱（方法論，值得記住）

### 陷阱一：instrumentation 自己造成了它要量的現象

WSL2 底下各 NVML 查詢的成本差兩個數量級（`_nvml_cost.py` 實測）：

```
clock_sm            0.158 ms
power               0.118 ms
temperature         0.062 ms
utilization         0.507 ms
throttle_reasons   18.283 ms   ← 差 100 倍
```

第一版把 `throttle_reasons` 放進逐句迴圈、推論前後各一次，
**每句偷偷插入 40ms 的空檔**。結果：
「連續模式」實際上變成「每 40ms 到達一次」，時脈爬不上去，
量到的降頻有一部分是量測工具自己造成的。

修正前後的差異（同一個 `gap=0` 條件）：

| | 30 秒內跑幾句 | 結束時 SM |
|---|---:|---:|
| 汙染版（每句 +40ms） | 476 | 712 MHz |
| 修正版（每句 +0.7ms） | **1128** | **1912 MHz** |

> **教訓：量毫秒級延遲時，任何 instrumentation 都要先量它自己的成本。**
> 反例資料留在 `results/exp1_sweep_cuda_v1_interleaved.jsonl`。

### 陷阱二：NVML 回報的時脈是落後指標

decay 實驗的 recover 階段：
**第 3 句起延遲已回到 16ms，但 NVML 連續 0.74 秒還回報 210 MHz。**

依 NVML 回報值分組，會得到自相矛盾的結果：

| NVML 回報 SM | n | 中位延遲 |
|---:|---:|---:|
| 210 MHz | 25 | **15.8ms** |
| 1927 MHz | 82 | 23.0ms |

「210 MHz 比 1927 MHz 快」顯然不對，是取樣延遲造成的假象。

> **教訓：NVML 時脈只能看穩態（某個到達率下長期停在哪），
> 不能做逐句關聯。**

### 陷阱三（既有數據的重新解讀）

原始 open_questions 表格裡的「GPU 連續 17.0ms」與本次量到的 17.5ms 吻合，
「GPU 間隔 134.3ms」與本次 gap≥2s 的 137~139ms 也吻合。
**原始量測是對的，結論也是對的，只是缺了時脈證據。現在補上了。**

## 實驗 2 — 各種熱啟動手段的效果與代價

`exp2_keepalive.py --gap 1.5 --n 25`
固定到達間隔 1.5 秒（模擬真實說話停頓），比較背景心跳的效果。

| 條件 | **p50** | p95 | SM 時脈 | 功耗 | 心跳次數 |
|---|---:|---:|---:|---:|---:|
| **none（對照組）** | **128.1** | 140.2 | 285 | 13.94W | 0 |
| matmul 256² @500ms | 128.9 | 139.3 | 277 | 13.29W | 86 |
| matmul 256² @250ms | 125.2 | 139.6 | 330 | 13.31W | 170 |
| matmul 256² @100ms | 125.0 | 139.5 | 360 | 13.34W | 424 |
| matmul 256² @50ms | 127.1 | 139.2 | 360 | 13.45W | 844 |
| matmul 1024² @100ms | 127.2 | 143.2 | 360 | 13.63W | 424 |
| **完整 dummy 推論 @500ms** | **60.6** | 119.7 | 525 | 15.25W | 83 |
| **完整 dummy 推論 @250ms** | **59.5** | 94.9 | 570 | 16.04W | 165 |
| **完整 dummy 推論 @100ms** | **46.3** | **86.7** | 510 | 19.23W | 407 |
| load（模擬 Moshi 佔用）@50ms | 68.5 | **83.5** | 667 | 18.56W | 816 |

### 三個結論

**① 便宜的心跳完全無效。**
小 matmul 不管間隔多短（甚至 50ms）、不管做多大（1024²），
延遲都停在 125~129ms，跟什麼都不做沒有差別。
即使 NVML 回報的時脈確實從 285 升到 360 MHz，**延遲一點也沒改善**。

> 這是最反直覺的一條。「隨手寫個 keep-alive 迴圈丟個小 kernel」
> 是直覺上最自然的做法，**而它沒有用**。

**② 真正的變數是「工作佔比（duty cycle）」，不是「有沒有心跳」。**

把每個條件換算成「心跳佔用 GPU 的時間比例」（用 3050 約 9 TFLOPS fp32 粗估）：

| 條件 | 單次工作量 | 佔比 | p50 |
|---|---:|---:|---:|
| matmul 256² @50ms | ~0.004ms | **0.008%** | 127.1 |
| matmul 1024² @100ms | ~0.24ms | **0.24%** | 127.2 |
| load 8×1024² @50ms | ~1.9ms | **3.8%** | 68.5 |
| dummy 推論 @500ms | 16ms | **3.2%** | 60.6 |
| dummy 推論 @250ms | 16ms | **6.4%** | 59.5 |
| dummy 推論 @100ms | 16ms | **16%** | 46.3 |

**佔比與延遲的對應關係很乾淨**：
<1% → 完全無效；約 3~6% → 降到 60~68ms；16% → 降到 46ms。
兩個佔比接近的條件（load 3.8% 與 dummy@500ms 3.2%）結果也接近（68.5 vs 60.6）。

> 所以正確的說法不是「心跳必須是真實推論」，而是
> **「心跳必須佔掉 GPU 至少百分之幾的時間才有用」**。
> 用完整推論當心跳只是達成這個佔比最方便的方式
> （剛好一次就有 16ms 的工作量），不是因為它「真實」。
>
> 這個框架也讓代價變得可以估算：**要買到 2.8 倍的延遲改善，
> 得付出 16% 的 GPU 時間**——而那 16% 是要從 Moshi/JoyGen 手上拿的。

**③ 有效，但天花板約 46~60ms，拿不回 17ms。**
最好的條件（dummy 推論 @100ms）也只把時脈拉到約 510 MHz，
離連續模式的 1912 MHz 差得遠。
**「維持熱啟動」做得到 2.8 倍改善，做不到 7.3 倍。**
外推上面那張表：要回到 17ms 大概得把佔比推到接近 100%，
那已經不是心跳，是常駐佔用整張卡。

### 代價

| | none | dummy@100ms | 差 |
|---|---:|---:|---:|
| 功耗 | 13.94W | 19.23W | **+5.3W（+38%）** |
| GPU 工作量 | 每 1.5 秒 16ms | 每 0.1 秒 16ms | **15 倍** |

**這 15 倍的 GPU 工作是要跟 Moshi / JoyGen 搶的。**
本實驗沒有量「心跳對其他模型造成多少延遲」——
那需要真的把 Moshi 接上來才測得準。

### `load` 條件（模擬 Moshi 也在用卡）的特別意義

`load` 是一個背景執行緒每 50ms 連跑 8 次 1024² matmul，
用來模擬 open_questions 裡那個但書：「真實 pipeline 中 GPU 可能根本不會閒置」。

結果：**p50 68.5ms、p95 83.5ms（全場最佳 p95）。**

→ **這支持了那個但書**：如果 Moshi 真的持續佔用 GPU，
  BERT 會自動受惠，不需要自己寫心跳。
  而且 p95 是全場最好的——因為時脈被穩定維持住，變異變小了。

⚠️ 但這只是模擬。真實的 Moshi 除了「維持時脈」還會 **搶 SM**，
  淨效果是好是壞，只有真的接上去才知道。

## 實驗 3 — 降低單次成本（fp16 / torch.compile / CUDA Graph）

`exp3_reduce_cost.py --n 25`
「間歇」= 到達間隔 1.5 秒（就是最痛的那個情境）。
`pad` = 是否 padding 到固定 64 token（CUDA Graph 必須固定形狀）。

| 變體 | dtype | pad | 連續 p50 | **間歇 p50** | 間歇 p95 | VRAM | 暖機 |
|---|---|---|---:|---:|---:|---:|---:|
| **eager（現況）** | fp32 | ✗ | 15.97 | **126.5** | 139.1 | 1073 MB | 1.2s |
| eager_padded | fp32 | ✓ | 17.02 | 140.4 | 152.0 | 1074 MB | 0.9s |
| **fp16** | fp16 | ✗ | 16.22 | **61.9** | 63.6 | **547 MB** | 1.1s |
| compile_default | fp32 | ✓ | 11.96 | 137.5 | 146.1 | 1074 MB | 17.6s |
| compile_reduce_ov | fp32 | ✓ | 11.94 | 136.2 | 142.8 | 1065 MB | 14.4s |
| **compile_ro_fp16** | fp16 | ✓ | **4.69** | **52.4** | **53.6** | **539 MB** | 15.5s |

### 這張表是整份調查最有價值的結果

**① fp16 一項就把間歇延遲砍掉一半（126.5 → 61.9ms），而且 VRAM 減半。**

- 不用心跳、不用改驅動設定、不用多耗一瓦電
- **VRAM 1073 → 547 MB**，在這張只有 4GB、還要跟 Moshi/JoyGen 共用的卡上，
  這個附帶好處可能比延遲更重要
- 連續模式幾乎沒差（16.2 vs 16.0）——因為滿速時這個模型太小，
  瓶頸不在計算；**低時脈時才顯出差別**，正好對症

⚠️ **但 fp16 會不會賠準確率？→ 見實驗 4，答案是幾乎不會。**

**② torch.compile 只改善連續模式，對間歇模式毫無幫助。**

- 連續：15.97 → 11.94ms（改善 25%，符合「省下 kernel launch overhead」的預期）
- 間歇：126.5 → 136.2ms（**反而變差**，因為要 padding 到 64）

原因很清楚：CUDA Graph 省的是 **CPU 端的 kernel launch overhead**，
而間歇模式的瓶頸是 **GPU 在低時脈下算得慢**。省 CPU 的時間治不了 GPU 的病。

> 這修正了 `survey/02` 裡「CUDA Graph 對 batch=1 短序列特別對症」的預期。
> **對症的是「連續模式」，不是「間歇模式」。**

**③ 兩個一起用才是最佳解：4.69ms 連續 / 52.4ms 間歇。**

- 連續比 eager 快 **3.4 倍**（15.97 → 4.69ms）
- 間歇比 eager 快 **2.4 倍**（126.5 → 52.4ms）
- p95 從 139.1 收斂到 **53.6ms**（變異幾乎消失）
- 而且這是 **唯一同時改善兩種模式** 的組合

**④ padding 的代價要記住：+11% 間歇延遲**（126.5 → 140.4ms）。
compile 的收益是扣掉這個代價之後才算的淨值。
如果之後 padding 長度調得更貼近實際 token 分布，收益還會再好一點。

### 跟其他路線並排比較（間歇 1.5 秒）

| 方案 | p50 | p95 | 額外功耗 | 額外 GPU 佔用 | VRAM |
|---|---:|---:|---:|---:|---:|
| 現況（eager fp32） | 126.5 | 139.1 | — | — | 1073 MB |
| CPU（既有數據） | 94.6 | — | — | — | 0 |
| 心跳 dummy@100ms | 46.3 | 86.7 | +5.3W | **+16%** | 1073 MB |
| **fp16** | 61.9 | 63.6 | 0 | 0 | **547 MB** |
| **fp16 + CUDA Graph** | **52.4** | **53.6** | 0 | 0 | **539 MB** |

> **結論很清楚：C 路線（降低單次成本）完勝 B 路線（心跳）。**
> 心跳的 p50 略好（46.3 vs 52.4），但它的 p95 差得多（86.7 vs 53.6），
> 而且要付 16% 的 GPU 時間與 5.3W——那 16% 是要跟 Moshi/JoyGen 搶的。
> **fp16 + CUDA Graph 是完全免費的，還順便省下一半 VRAM。**
>
> 而且兩者 **不衝突**，真的需要的話可以疊加。

## 實驗 4 — fp16 賠了多少準確率：幾乎沒有

`exp4_fp16_parity.py`
同一個模型、同一批句子，**只差 dtype**，所以任何差異都純粹來自精度。

### 200 句同領域樣本（`_local/samples.jsonl`）

```
標籤一致率      1.0000   （0 / 200 句不一致）
信心平均絕對差  0.001391  最大 0.020817
機率向量最大差  平均 0.001451  最大 0.020897
準確率          fp32 0.85    fp16 0.85
```

**一句都沒有換答案。** 信心的差異在小數點後第三位，
最大也只有 0.021——遠小於「0.90 vs 0.95」這種實務上會用到的區分度。

> 這代表 **fp16 對下游而言是完全透明的**：
> `emotion` 欄位一模一樣，`confidence` 欄位差在第三位小數。
> 換過去不需要重新校準、不需要重新定門檻、不需要跟品靜溝通。

⚠️ **限制與一個該注意的風險**：

1. 這只驗了 200 句同領域樣本。fp16 的風險在 **極端 logits**（絕對值很大的數）上，
   而那種情況在跨領域資料上比較容易出現 → 另外跑了 1200 句 SMP2020 的對照。
2. **這個模型是 DeBERTa-v2/v3 架構**（實測 config：`DebertaV2ForSequenceClassification`，
   底層 `MoritzLaurer/mDeBERTa-v3-base-mnli-xnli`）。
   DeBERTa 的 disentangled attention 在社群上 **有 fp16 溢位的回報**。
   我們實測沒遇到，但這代表 **換模型時 fp16 的 parity 要重驗一次**，
   不能假設「上次沒事這次也沒事」。
   → `exp4_fp16_parity.py` 就是為了讓這件事變成一行指令。

## 實驗 5 — TF32：沒用，不要開

`exp3_reduce_cost.py --n 25 --only tf32 eager --tag tf32`

Ampere 以後的卡可以用 TensorFloat-32 跑 fp32 的矩陣乘法
（尾數 10 bit、指數範圍同 fp32）。torch 2.x 預設關閉，開起來只要兩行：

```python
torch.backends.cuda.matmul.allow_tf32 = True
torch.backends.cudnn.allow_tf32 = True
```

跑 compile 時 torch 甚至會主動跳警告建議開它。實測：

| 變體 | 連續 p50 | 連續 p95 | 間歇 p50 | 間歇 p95 |
|---|---:|---:|---:|---:|
| eager（同一輪的對照） | **16.93** | **35.17** | 126.78 | 139.90 |
| tf32 | 22.51 | 46.35 | **118.71** | **128.30** |

**連續模式反而慢了 33%**（16.93 → 22.51ms），
間歇模式只快 6%（126.78 → 118.71ms）。

推測原因：這個模型太小、序列太短，TF32 換來的算力用不上，
反而因為走了不同的 kernel 路徑（cuBLAS 對 TF32 會挑不同的 GEMM 實作）
而付出額外成本。torch 那句警告是針對大模型的一般建議，**對我們不適用**。

> **結論：不要開 TF32。**
> 順帶一提，這也說明了「編譯器/框架的效能建議要實測」——
> 同一輪裡 fp16 賺兩倍，TF32 卻虧 33%，兩者都是「降低精度換速度」。

### 1200 句跨領域測試集（`eval/data/testset/dataset_v1.jsonl`，zh_tw）

```
標籤一致率      0.9950   （6 / 1200 句不一致）
信心平均絕對差  0.003914  最大 0.069144
機率向量最大差  平均 0.004239  最大 0.069144
```

**六句不一致的，全部都是模型本來就在猶豫的句子**：

| fp32 | 信心 | fp16 | 信心 |
|---|---:|---|---:|
| 平淡語氣 | 0.2543 | 驚奇語調 | 0.2597 |
| 悲傷語調 | 0.2771 | 疑問語調 | 0.2840 |
| 關切語調 | 0.4319 | 疑問語調 | 0.4169 |
| 開心語調 | 0.2887 | 憤怒語調 | 0.2985 |
| 疑問語調 | 0.3602 | 憤怒語調 | 0.3751 |
| 疑問語調 | 0.4409 | 平淡語氣 | 0.4408 |

**信心全部在 0.25~0.44 之間**——也就是說 fp16 只在
「第一名跟第二名幾乎打平」的時候才會改變答案。
最後那一句甚至是 0.4409 vs 0.4408，差 0.0001。

> **這正是我們想要的行為**：fp16 的誤差量級（~0.004）
> 遠小於模型自己的不確定度，只在本來就是擲硬幣的地方翻面。
> **在模型有把握的句子上，fp16 一句都沒改。**
>
> 而且這 6 句在 fp32 下本來也大多是答錯的
> （這個測試集整體準確率只有 0.408）。

## 實驗 6 — fp16 ＋ 心跳：兩條路可以疊加，而且要疊

昨晚的 `exp2`（心跳）跑的是 fp32、`exp3`（fp16）沒開心跳，
**組合從來沒量過**。2026-08-13 補測，同樣 gap=1.5s、30 句/條件：

| 條件（全部 fp16） | p50 | p95 | 穩態 SM | 功耗 | 心跳次數 |
|---|---:|---:|---:|---:|---:|
| none（fp16 基準） | 62.7ms | **65.0ms** | 210 MHz | 13.6W | 0 |
| model_fwd @500ms | 59.8ms | 86.0ms | 210 MHz | 13.9W | 98 |
| model_fwd @250ms | 58.8ms | 93.0ms | 273 MHz | 14.4W | 197 |
| model_fwd @100ms | 39.8ms | 77.0ms | 484 MHz | 16.0W | 483 |
| model_fwd @50ms | **38.1ms** | 60.7ms | 686 MHz | 18.6W | 961 |
| load_1024x8 @50ms | 41.7ms | **45.9ms** | 638 MHz | 18.5W | 960 |

對照 fp32 版（`exp2_keepalive_gap1.5.meta.json`）：

| 條件 | fp32 p50 | fp16 p50 | fp32 p95 | fp16 p95 |
|---|---:|---:|---:|---:|
| none | 128.1ms | 62.7ms | 140.2ms | 65.0ms |
| model_fwd @100ms | 46.3ms | 39.8ms | 86.7ms | 77.0ms |
| load_1024x8 @50ms | 68.5ms | 41.7ms | 83.5ms | 45.9ms |

### 四個結論

**1. 疊加有效，但邊際效益遞減。**
fp16 單獨把 126→62.7ms（省 64ms），
再加最重的心跳只再省 24.6ms（62.7→38.1）。
先做 fp16 是對的順序 —— 它拿走了大部分的收益且免費。

**2. 稀疏心跳會讓 p95 變差，這是新發現。**
`none` 的 p95 是 65.0ms，但 @500ms / @250ms / @100ms 的 p95 分別是
86.0 / 93.0 / 77.0ms —— **比不做心跳還糟**。
原因是心跳跟主推論搶同一張卡：心跳雖然在獨立 stream，
硬體 SM 只有一組，運氣不好時請求剛好排在心跳後面。
心跳夠密（@50ms）時時脈拉得夠高，才把這個懲罰蓋過去。
→ **心跳要嘛不做，要嘛做滿。半吊子的心跳是最差的選擇。**

**3. `load` 條件（模擬 Moshi 也在用卡）的 p95 最好，45.9ms。**
持續穩定的背景負載 > 週期性脈衝：
時脈被抬到差不多的高度（638 vs 686 MHz），
但因為負載是連續的，沒有「心跳剛好卡在前面」的尖峰。
**這是目前所有組態裡 p95 最低的一個**，
也再次指向同一件事：真實 pipeline 裡 Moshi 若持續佔卡，
我們什麼都不用做就能拿到這個數字。

**4. 心跳打不破時脈天花板 —— 這是它的結構性限制。**
即使 @50ms（duty cycle 已經很高），穩態時脈也只到 686 MHz，
離連續模式的 1912 MHz 還差 2.8 倍。
用三個點（210→62.7、686→38.1、1912→16.2）配 `延遲 ≈ a + b/時脈`：

```
a ≈ 10.5ms（跟時脈無關的固定成本）
b ≈ 11000
```

代入 1200 MHz → **預測約 19.6ms**。
也就是說 **`-lgc` 鎖 1200MHz 的效果會遠好過任何心跳**
（19.6ms vs 38.1ms），而且不花 GPU 時間、不花電、不用背景執行緒。
心跳之所以只能到 686MHz，是因為驅動的 boost governor
要看到「持續重載」才給滿血時脈，週期性脈衝騙不過它。

### 代價

+5.0W（13.6 → 18.6W）、約 16% GPU 時間，跟 fp32 時期一樣。
差別是現在買到的東西變少了（fp16 已經先拿走大部分收益），
**投資報酬率比昨晚估的更差**。

### 還沒測的組合

- `fp16 + CUDA Graph + 心跳` —— 預期 p50 落在 30ms 上下，但 `exp2`
  用的是 `EmotionClassifier`、`exp3` 用的是自己建的變體，要先把兩邊接起來。
- `-lgc` 鎖時脈後的一切 —— 需要管理員權限，見上。

## CPU 對照組

`exp1_gap_sweep.py --mode sweep --device cpu --n-per-gap 25`
同一台機器、同一個容器、12 核。

| 到達間隔 | n | p50 | p95 |
|---:|---:|---:|---:|
| 連續 (0s) | 308 | 98.3 | 108.3 |
| 0.05s | 201 | 100.2 | 115.3 |
| 0.1s | 147 | **106.6** | 122.1 |
| 0.2s | 103 | 92.7 | 110.8 |
| 0.35s | 69 | 89.3 | 99.3 |
| 0.5s | 52 | **86.1** | 100.1 |
| 0.75s | 36 | 88.7 | 98.1 |
| 1.0s | 28 | 90.2 | 96.3 |
| 1.5s | 25 | 91.5 | 100.6 |
| 2.0s | 25 | 90.9 | 99.3 |
| 3.0s | 25 | 88.0 | 104.1 |
| 5.0s | 25 | 92.5 | 104.8 |

**CPU 幾乎是一條水平線（86~107ms），而且方向與 GPU 相反**：
連續模式 98.3ms 反而比間隔模式的 86~92ms **慢約 10%**。

這重現了原始觀察（CPU 連續 105.1ms vs 間隔 94.6ms，慢 11%），
機制在 `survey/01` 第 2.4 節：CPU 的 idle 退出是微秒級，
沒有 GPU 那種降頻問題；連續跑反而累積熱、turbo 回落。

⚠️ **兩個 caveat**：
1. 這次量到的 86~107ms 比原始的 94.6ms 略有出入，
   因為 **沒有固定執行緒數**（`eval/configs/models.yaml` 有
   `torch_num_threads: 4` 的設定，但 `imood_emotion/classifier.py` 沒有套用）。
   容器內 12 核全開，數字會隨機器負載浮動。
   → **要拿 CPU 數字做決策前，先把執行緒數固定住。**
2. CPU 跑的時候 GPU 完全閒著，反之亦然。真實 pipeline 兩者都在忙，
   互相搶記憶體頻寬，數字都會變差。

### 最終對照（間隔 1.5 秒 = 真實說話停頓）

| | p50 | p95 | VRAM |
|---|---:|---:|---:|
| CPU | 91.5ms | 100.6ms | 0 |
| GPU 現況（eager fp32） | 125.3ms | 140.9ms | 1073MB |
| GPU + 心跳 dummy@100ms | 46.3ms | 86.7ms | 1073MB |
| **GPU + fp16** | **61.9ms** | **63.6ms** | **547MB** |
| **GPU + fp16 + CUDA Graph** | **52.4ms** | **53.6ms** | **539MB** |

**GPU 現況確實輸給 CPU（125.3 vs 91.5）——原始分析沒有錯。**
**但只要改成 fp16，GPU 就贏回來（61.9 vs 91.5），加 CUDA Graph 再拉開到 52.4ms。**
而且 p95 差距更大：GPU+fp16+Graph 是 53.6ms，CPU 是 100.6ms，**幾乎兩倍**。

> 這就是這份調查對「CPU vs GPU」爭議的最終答案：
> **兩邊都對，只是都在比錯的組態。** 比的應該是
> 「CPU fp32」對「GPU fp16 + CUDA Graph」，不是「CPU」對「GPU」。
