# 02 — 有哪些解法：三條路

> 01 篇確認問題是 **DVFS 降頻（L4）**。
> 解法可以分成三條完全不同的路，混在一起討論會很亂：

| 路線 | 思路 | 代表手段 |
|---|---|---|
| **A. 不讓它降頻** | 從驅動/硬體層面禁止降頻 | 鎖時脈、persistence mode、電源策略 |
| **B. 讓它以為很忙** | 用假負載騙過 governor | 心跳（keep-alive）、背景常駐工作 |
| **C. 降低單次成本** | 承認會降頻，但讓 210 MHz 也夠快 | CUDA Graph、torch.compile、ONNX/TensorRT、換小模型、留在 CPU |

**C 常常被忽略，但對我們可能是最實際的一條** —— 見 03 篇的取捨。

---

## A. 不讓它降頻

### A1. `nvidia-smi --lock-gpu-clocks` (`-lgc`)

```bash
nvidia-smi -lgc 1900,2100      # 鎖定 SM 時脈範圍
nvidia-smi -rgc                # 解除
nvidia-smi -lmc <min>,<max>    # 記憶體時脈（-rmc 解除）
```

這是最直接的做法：**直接告訴驅動不准降頻**。

**我們的實測結果：❌ 在 WSL2 容器內失敗。**

```
$ nvidia-smi -lgc 1000,2100
Unable to set GPU locked clocks "(gpuClockMin 1000, gpuClockMax 2100)"
for GPU 00000000:01:00.0: Unknown Error
```

原因：WSL2 的 nvidia-smi 是轉發到 Windows 驅動的 shim，
這類「設定型」呼叫多半沒有實作。
（另外文獻上也提到 **部分筆電 GeForce 本身就不支援 `-lgc`**，
即使在原生 Linux 上也會回報 not supported。所以就算換原生 Linux 也不保證能用。）

⚠️ 注意 `nvidia-smi -ac`（application clocks）**已被 NVIDIA 標為 deprecated**，
新做法一律用 `-lgc`/`-lmc`，別再參考舊文章的 `-ac` 寫法。

### A2. Persistence Mode（`nvidia-smi -pm 1`）

**這個常被誤解。** Persistence mode 是「沒有程式在用 GPU 時，
驅動仍然保持載入狀態」，解決的是 **L1/L3 的驅動初始化延遲**，
**不是時脈降頻**。

而且它在 Windows/WSL2 上不適用（Windows 的 WDDM 驅動模型本來就常駐）。
我們實測 `nvidia-smi -pm 1` 回報「already Enabled」，但時脈照樣掉到 210 MHz
——**證明它解決的不是這個問題**。

> 📌 記住這條：**看到文章推薦「開 persistence mode 解決 GPU 慢啟動」，
> 對我們沒用。** 那是在解 L1/L3。

### A3. Windows 端：NVIDIA 控制面板「偏好最大效能」

**這條在我們的環境最有希望**，因為它繞過了 WSL2 的限制——
設定在 Windows 驅動層，容器裡的 CUDA 一樣受惠。

```
NVIDIA 控制面板 → 管理 3D 設定 → 電源管理模式
  預設「最佳電源」/「Optimal Power」
  → 改成「偏好最大效能」/「Prefer Maximum Performance」
```

文獻/社群說法：
> 「Maximum Performance 會把 GPU 時脈釘在高檔，消除 ramp-up 造成的卡頓。
>  代價是閒置時多吃 10~30W。」

但要注意兩個但書：

1. 名字是 **「偏好」**最大效能不是「總是」——
   **它仍然受溫度、功耗、噪音上限限制**。
   在一台 60W power limit 的筆電上，效果可能打折。
2. 這個設定可以 **針對單一程式** 設定（在「程式設定」分頁選執行檔）。
   但我們的 CUDA 程式跑在 WSL2 容器裡，
   **主機看到的執行檔是 `vmmem`/WSL 相關的 process，不是我們的 python**
   ——所以只能用「全域設定」，會影響整台機器。

**⚠️ 這條需要在 Windows 主機上手動操作 + 實測驗證，我沒有代為更動系統設定。**
建議 Gino 自己試：改設定 → 重跑 `exp1 --mode sweep` → 比較。
這是整份調查裡 **唯一一個「可能一次解決問題」的手段**。

### A4. 註冊表 KBOOST / SetStablePowerState（不建議）

- **KBOOST**（regedit 強制鎖最高頻）：超頻社群的做法，
  對系統穩定性與壽命有風險，而且是全域的。**不建議。**
- **SetStablePowerState**（DirectX 12 API）：
  NVIDIA 官方文件講得很清楚，這是 **給 profiling 用的**，
  而且 **它不鎖記憶體時脈**，NVIDIA 自己說「不要只靠它」。
  它鎖的是「stable clock」（通常比 boost 低），
  目的是讓量測可重現，不是讓程式跑最快。**不是我們要的東西。**

## B. 讓它以為很忙（心跳 / keep-alive）

### B1. 原理

既然 governor 是看「最近有沒有負載」決定要不要降頻，
那就用一個背景執行緒週期性丟一點小工作進去，讓它一直看到負載。

```python
# 概念示意
def heartbeat():
    a = torch.randn(256, 256, device="cuda")
    while running:
        torch.matmul(a, a)          # 便宜的假工作
        torch.cuda.synchronize()
        time.sleep(0.05)            # 每 50ms 一次
```

### B2. 要調的三個參數

| 參數 | 影響 | 從我們的降頻曲線推 |
|---|---|---|
| **間隔** | 太長就來不及維持 | 實測 0.73 秒時已從 1927 掉到 1170 MHz，**間隔要 ≪ 0.5 秒** |
| **工作量** | 太小 governor 可能不當一回事；太大就是在燒電、跟真實請求搶資源 | 需要實測掃描 |
| **CUDA stream** | 用獨立 stream，避免真實請求排在心跳後面 | `torch.cuda.Stream()` |

### B3. 已知的代價

1. **功耗**：實測連續負載 42~49W vs 閒置 15W。心跳的功耗會落在中間，
   **這張 4GB 卡要跟 Moshi/JoyGen 共用，多吃的電與熱是實打實的成本。**
2. **熱**：實測連續推論 8 秒溫度就上到 78~84°C。
   筆電長期高溫會觸發 HW thermal slowdown，反而更慢。
3. **與其他模型搶資源**：心跳會佔用 SM，Moshi/JoyGen 的延遲可能因此上升。
   **這是最需要實測的一點** —— 如果為了 BERT 省 100ms，
   卻讓 Moshi 多 50ms，整體是不是划算要算過。
4. **這是 hack**：正式部署到雲端 GPU 時，環境的電源策略可能完全不同，
   心跳可能沒必要（甚至有害）。**別把它寫死進 production 邏輯，要能關掉。**

### B4. 一個關鍵的但書（open_questions 裡本來就寫了）

> 「真實 pipeline 中 Moshi、JoyGen 同時運作，GPU 可能根本不會真的閒置，
>  屆時整個『間歇輸入降頻』的前提可能都不成立。」

**這個但書非常可能成立，而且如果成立，B 路線就完全不需要做。**

Moshi 是即時語音模型，它在對話期間 **幾乎一直在跑**。
如果 Moshi 把時脈維持在高檔，BERT 就搭便車了——
**免費的心跳，還不用自己燒電。**

→ `exp2_keepalive.py` 特地加了一個 `load` 條件模擬這件事。
→ **這是整個 GPU 問題裡最該優先確認的事**：
  與其研究怎麼自己做心跳，不如先確認 Moshi 在不在旁邊跑。

## C. 降低單次成本（承認會降頻，但讓它不痛）

**這條路的邏輯**：與其對抗電源管理，不如讓單次推論便宜到
「就算在 210 MHz 也夠快」。目標是把 130ms 壓到可接受範圍。

### C1. CUDA Graph / `torch.compile(mode="reduce-overhead")`

**原理**：把整串 kernel launch 錄成一張圖，之後用一次 CPU 呼叫重放，
省掉每個 kernel 約 5~10μs 的 launch overhead。

文獻說法：
> 「小 batch 時，eager 模式的 kernel dispatch CPU overhead 可佔總時間的 20~30%。」
> 「CUDA Graph 在小 batch、框架 overhead 主導的情況下，能大幅降低延遲。」

**預期它對我們特別有效，因為**：
- batch=1、序列短（max_length 160，實測 p99 字數 139）
- 這正是「kernel 又多又小、launch overhead 佔比高」的典型情境

**但要注意**：
- CUDA Graph 需要 **固定形狀的輸入**。我們的句子長度不一，
  要 **padding 到固定長度**（例如固定 padding 到 64 或 160 token）。
  padding 會增加實際計算量，可能吃掉一部分收益 —— **要實測才知道淨效果**。
- `torch.compile` 第一次編譯要幾十秒，要算進 warmup。

> ⚠️ **實測之後這段預期要修正（見 `RESULTS.md` 實驗 3）**：
> torch.compile + CUDA Graph **只改善連續模式（15.97 → 11.94ms，快 25%），
> 對間歇模式毫無幫助（126.5 → 136.2ms，還因為 padding 略微變差）**。
>
> 原因回頭看很清楚：CUDA Graph 省的是 **CPU 端的 kernel launch overhead**，
> 而間歇模式的瓶頸是 **GPU 在 210~500 MHz 下算得慢**。
> **省 CPU 的時間治不了 GPU 的病。**
>
> 我原本寫「這件事跟降頻正交，同時改善兩種模式」——**那句是錯的**，
> 留在這裡當作「聽起來合理的推論也要實測」的例子。

### C1b. fp16（半精度）—— 實測才發現這才是主角

原本沒把 fp16 當重點（以為只是「省記憶體」），實測結果完全相反：

| | eager fp32 | fp16 | 改善 |
|---|---:|---:|---|
| 連續 p50 | 15.97ms | 16.22ms | 幾乎沒差 |
| **間歇 p50** | **126.5ms** | **61.9ms** | **2.0 倍** |
| 間歇 p95 | 139.1ms | 63.6ms | 2.2 倍 |
| VRAM | 1073 MB | **547 MB** | **少一半** |

**為什麼只在間歇模式有效**：滿速時這個模型太小，瓶頸不在算力；
低時脈時算力與記憶體頻寬都變成瓶頸，fp16 把兩者的需求都減半。
**它剛好只在痛的時候止痛。**

而且 **VRAM 減半** 對這張 4GB、要跟 Moshi/JoyGen 共用的卡，
可能比延遲改善還重要。

**fp16 + torch.compile(reduce-overhead) 一起用**：
連續 **4.69ms**、間歇 **52.4ms**、p95 **53.6ms** —— 全場最佳。

⚠️ 唯一要付的代價是精度，見 `RESULTS.md` 實驗 4 的準確率對照。

### C2. ONNX Runtime / TensorRT / INT8

文獻上的量級：
- 量化：模型小 4 倍、快 2~3 倍
- TensorRT INT8：4 倍以上加速

**但對我們有幾個現實問題**：
- TensorRT 要為特定 GPU 型號 build engine，換卡要重 build
  （本機 3050 → 實驗室機 → 雲端，會有三份）
- INT8 需要校準資料，且會影響準確率——
  而準確率已經是弱項（憤怒 60%），不太經得起再掉
- 增加一整套依賴與建置流程，跟「容器單一職責」的架構決策有點衝突

→ 建議：**ONNX Runtime（FP32/FP16）可以試，TensorRT INT8 現階段不划算。**

### C3. 最誠實的一條：**留在 CPU**

原始數據：CPU 間歇 94.6ms，GPU 間歇 134.3ms。
**如果 C1/C2 都做不出來，CPU 本來就是比較快的選項。**

而且 CPU 路線有幾個結構性優點：
- 沒有降頻問題（CPU 的 idle 退出是微秒級）
- **把 4GB VRAM 完整留給 Moshi/JoyGen** —— 這張卡只有 4GB，
  BERT 實測就吃掉 1.08GB（`torch_peak_allocated_mb: 1084.4`），
  佔了 27%
- 延遲變異小、可預測

## D. 一個容易踩的坑：別把「量測方法」當成解法

搜 "GPU warm up" 會大量看到：

- 「服務啟動後跑幾次 dummy inference 再開始服務」→ 這是 **L3**，我們已經在做（`--warmup 20`）
- 「pre-warmed container / 避免 scale-to-zero」→ 這是 **L1**，我們沒這問題
- 「model weight streaming」→ **L2**，我們沒這問題

**這三個都不解決 L4。** 判斷一篇文章有沒有講到我們的問題，
最快的方法是看它有沒有提到 **`clocks.sm` 或 DVFS**。沒提到就是在講別的層次。

## 三條路的比較

| | A 鎖時脈 | B 心跳 | C 降低成本 |
|---|---|---|---|
| 本機可行性 | ❌ 容器內鎖不了；A3 待實測 | ✅ 純程式，可行 | ✅ 可行 |
| 雲端可行性 | ✅ 資料中心卡通常可以 `-lgc` | ⚠️ 可行但可能沒必要 | ✅ |
| 對 Moshi/JoyGen 的影響 | 中（全卡都鎖高頻，多耗電） | **大（直接搶 SM）** | 無 |
| 額外功耗 | 高 | 中 | 無 |
| 實作成本 | 低（一行指令） | 低 | 中~高 |
| 是不是 hack | 否 | **是** | 否 |
| 換環境會不會失效 | 會（每個環境不同） | 會 | **不會** |

---

## 這一篇的結論

1. **A1 鎖時脈在 WSL2 容器內確定不行**（實測 Unknown Error）。
2. **A2 persistence mode 解的不是這個問題**，別被文章誤導。
3. **A3 NVIDIA 控制面板「偏好最大效能」是最有希望的一次性解法，
   但需要 Gino 在 Windows 主機上手動改 + 重測。**
4. **B 心跳可行但是 hack，而且會跟 Moshi/JoyGen 搶資源。
   最該先確認的是「Moshi 在跑的時候，還會不會降頻」——
   如果不會，B 整條路都不用做。**
5. **C 是唯一「換環境不會失效」的路**，其中
   **CUDA Graph / torch.compile 對 batch=1 短序列特別對症**，值得優先試。
6. 網路上多數 "GPU warm start" 資料在講 L1~L3，**跟我們的 L4 無關**。
